### PF-266 · The theme switcher, and the flash it must not have
`—` · **3 pts** · depends: PF-199 · standards: WCAG 2.2 AA · —

- [x] A person chooses among the five themes, and the choice is **persisted before the first paint** - a switcher that applies after hydration shows the wrong theme for a frame, and on a dark-theme user that frame is a white flash in a dark room
- [x] The preference follows the account rather than the browser, because somebody who set dark on their laptop did not ask to be blinded by their phone
- [x] `prefers-color-scheme` is the default for an account that has not chosen, and choosing overrides it - a product that ignores the system setting and one that refuses to let you leave it are both wrong
- [x] `prefers-contrast` and `prefers-reduced-transparency` select the high-contrast themes, since the people those settings exist for should not have to find a menu
- [x] **Found while building it:** Tailwind v4 defaults `dark:` to the media query, so a class-based toggle leaves every `dark:` utility compiling, landing in the HTML and doing nothing. `@custom-variant dark` is load-bearing and says so in the stylesheet

### PF-199 · The token architecture
`—` · **8 pts** · depends: PF-017 · standards: WCAG 2.2 AA · `risk:high`

- [x] Three layers: **primitive** (raw OKLCH ramps), **semantic** (role names like `surface`, `on-surface`, `outline`, `danger`), **component** (a token a component owns). A component never references a primitive
  - The third layer did not exist; the `--k-*` component tokens are new, and the scrollbars are the first component to own any. A check refuses a component token that reads a primitive, bitten by pointing `--k-scrollbar-thumb` at `--p-neutral-500`.
  - The layers are declared in `resources/css/token-architecture.json`, because they are statements a stylesheet cannot make about itself: which layer may read which, what role each family stands for, and the two literal-colour exceptions with their reasons.
- [x] OKLCH rather than hex or HSL, because it is perceptually uniform: a ramp generated by stepping lightness actually looks evenly stepped, and a contrast target is hit by adjusting one number instead of by trial and error
  - Bitten with a hex value, which is the form the first careless addition takes.
- [x] `--c-*` under `:root` and again under each theme's selector, mapped once inside `@theme`, so `text-primary` follows the theme with no `dark:` variant at the call site. **Five themes, not two** - light, dark, dark gradient, high-contrast light and high-contrast dark - because a high-contrast theme that is the dark theme with bolder text is not a high-contrast theme
  - **Exactly once** is now checked in both directions: a role mapped into `@theme` zero times and a role mapped twice both fail. `--c-debit` and `--c-credit` were defined by all five themes, declared in the contrast matrix, measured on every run - and mapped **nowhere**, so no template could use them and none did. A token nobody can read that a check faithfully measures is the worst kind of green.
  - And no template themes itself with a `dark:` colour variant, bitten by adding one to the theme switcher.
- [x] Tokens that deliberately do **not** invert are documented as such with the reason
  - Measured rather than asserted: light against Graphite, seven roles are identical. Six are the sidebar's and were documented; `--c-outline-control` was not. It is deliberate - a mid tone is what clears 3:1 against a near-white surface and a near-black one at once - and it is exactly the token somebody "fixes" with a dark value. The check bites both ways: emptying a reason fails, and giving a declared non-inverting token a different value in `.dark` also fails.
- [x] A token can only be added with a stated role; a token named after a colour rather than a role fails review
  - Not "fails review" - fails the build. `--c-teal-rule` fails for being named after a colour, and `--c-widget` fails for belonging to no stated family, so the two halves are separate failures with separate messages.

### PF-202 · Digit shaping
`—` · **3 pts** · depends: PF-201 · standards: CLDR, ICU · `type:compliance`

- [x] Digit shape is a **per-tenant setting** (`latn` / `arab`), applied through ICU, never by string replacement
  - It was anticipated and never built. `NumberingSystem::SHAPES` is commented "the names a tenant's own digit-shape setting uses" and maps six spellings - and no such setting existed; `config('money.display.digits')` was the only input. So this criterion had a mapping table for a setting nobody could set.
  - Three bites on the setting itself (a default of `arab`, `arabext` added to the allowed values, the scope moved to the entity) and two on the mechanism (a string-replacement shaping table added to `NumberingSystem`, and the `latn` subtag skipped when the answer is `latn`).
- [x] Financial documents in the region conventionally use Western digits even in Arabic text, so `latn` is the default and the setting exists because conventions differ by institution
- [x] Shaping applies to display only; stored values, exports, XML payloads and API responses are always Western digits
  - The seam is the middleware, registered in the **web** group only, and that is what keeps the shape display-only. Two bites: removing it from the group, and formatting `jsonSerialize()`'s amount through ICU - the second being the one that would quietly reshape every API response and every XML payload.
- [x] A test asserts an Arabic-shaped display value still parses and round-trips
  - With the setting at `arab`, a figure renders `١٬٢٣٤٫٥٦` and parses back to the same amount, while the wire form, the stored string and `(string)` stay Latin.
