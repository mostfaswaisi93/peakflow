# Phase 04 — The tax engine

**14 tasks · 71 points**

Tax comes before sales, and that ordering is the most consequential sequencing decision in the whole plan. The tax point date, the rate version and the per-rate-group breakdown are **inside an issued document and frozen there**. Retrofitting them means migrating immutable rows that a customer has already filed a return on, which is to say it is not possible.

The engine's organising principle is that **tax is data, not code**. A rate that changes on a date is a row. A jurisdiction's rounding rule is a row. A place-of-supply decision is a rule evaluated from rows. Nothing about a specific country is compiled into the sales path.

---

### PF-078 · Place of supply
`Tax` · **8 pts** · depends: PF-077, PF-060 · standards: — · `risk:high` `type:compliance`

- [x] A rule engine deciding which jurisdiction's tax applies, from: supplier country, customer country, customer registration status (B2B or B2C), item type (good, service, digital service), and the delivery location. Five conditions, a vocabulary of eight words, and no expressions - a rule book with a language in it is a program, and a program in configuration is a program nobody tests
- [x] Rules are data with a documented source per jurisdiction, and are evaluated in a defined precedence with the winning rule recorded on the document. Precedence is an **integer in the row**, not the row's position: array order is invisible in a diff, so a rule moved up three lines would change what thousands of documents charge and read as a reformatting. A check asserts that reversing the file's order changes nothing
- [x] Shipped cases: domestic, export of goods, intra-GCC, intra-EU B2B goods and services, digital services to consumers, and a documented fallback that **refuses rather than guesses**. Sixteen cases asserted on the winning rule **and the tax category** - a case asserting only the country would accept a reverse charge as a domestic sale whenever the two agree
- [ ] The decision and its reasoning are visible on the invoice's tax panel, because an accountant must be able to check it
- [x] `abroad` and `outside` are **two words**, and the distinction is the whole of intra-bloc treatment. Delivering from France to Germany is `abroad` and `bloc:eu`; to Switzerland it is `abroad` and `outside`. One is an intra-Community supply in category `K`, the other an export in `Z` that needs evidence of exit, and a single "is the customer foreign" flag collapses them invisibly - both answers carry a country and a rule id
- [x] A missing delivery location **refuses rather than falling through**. Continuing to a lower-precedence rule would answer a question that a higher-precedence rule had a claim on, and the answer would look ordinary: a country, a rule id, a legal source, and nothing saying the rule that should have decided was never evaluated. Measured with the refusal removed: goods with no delivery location resolved to the supplier's country by `domestic`
- [x] Bloc membership is validated against the vendored ISO 3166-1 register, not a regex. `ZZ` matches `/^[A-Z]{2}$/`, and **EU VAT identifiers are not ISO codes** - they use `EL` for Greece and `XI` for Northern Ireland, which is exactly what somebody copying from a VAT manual writes. A member no country record can equal never matches, and the bloc then answers "export" for a supply that is intra-bloc
- [x] The United Kingdom is recorded as a **dated departure**, not deleted. Deleting it answers correctly today and cannot answer anything about a supply made in 2019, and a credit note against a 2019 invoice is treated the way the original was. Measured with the date removed and GB back in the list: an intra-Community supply reported in category `K` for a country that left the Community
- [x] Found on the way: `bin/verify` evaluated every suite eagerly, so a suite that **threw** while being built aborted the whole run before a single line printed - 23 other checks went quiet because one configuration file was contradictory. Found by proving the bloc check bites: the deliberate contradiction was refused exactly as designed and took the run with it. A thrown exception is now a failed check and the suites after it still run

> The open criterion is a panel on an invoice, and invoices arrive in Phase 05. `PlaceOfSupplyDecision::explain()` already returns the sentence it will show, in Arabic and English, and the decision is `JsonSerializable` so the reasoning can be frozen onto the document rather than recomputed from party records that will have changed by the time anybody looks.

### PF-086 · Return generation
`Tax` · **8 pts** · depends: PF-085 · standards: — · `risk:high` `type:compliance`

- [x] A box-by-box return for a period, with **drill-down from every box to the journal lines behind it**. Assembled from the **ledger**, by tax point, from posted entries only - which is what makes PF-088's reconciliation possible: a return built from documents and a ledger posted from the same documents are two derivations of one truth, and when they disagree nothing says which is wrong
- [x] A pre-filing checklist: unposted documents in the period, unmatched bank lines, a non-zero suspense balance, documents missing evidence for their category
  - **Eight items, and none of them pending.** Five were built with the task; three were written out as `pending` with the phase that would bring each - documents with Phase 05, bank matching with Phase 08, evidence with a real document to record it against. All three arrived, so all three are now asked.
  - The check that guarded this was **inverted rather than deleted**: it used to assert at least three items were pending, and now it reports any that still are. A test demanding a gap would have to be satisfied by putting the gap back.
  - **"Unposted documents" is a different question from "draft entries"**, and both are kept. The draft check asks the ledger - an entry somebody left unposted. This asks the documents - an invoice or bill that was entered, carries a tax point in this period, and never reached the ledger at all. A document with no entry is invisible to the first check by construction: there is nothing to be draft.
  - **An unmatched bank line is a tax question**, not only a banking one: an unmatched receipt can be a sale nobody invoiced, which is output tax missing from this return. The money arrived, the authority's share did not, and the statement is the only record it happened. It is a warning on the banking screens and blocking here, because an unmatched line on a Tuesday is work to do and an unmatched line at filing is a figure somebody is about to swear to.
  - **The evidence item matters more than its position suggests.** The export zero rate claimed with no proof of exit is the most commonly assessed error there is: the authority does not prove the goods stayed, it asks the business to prove they left, and one that cannot pays the tax it did not charge on a sale whose margin assumed it would not. `EvidenceGate` already refuses at issue time, so a document reaching this check without evidence got here another way - an import, a migration, a category changed afterwards - which is exactly why it is asked again rather than trusted to the gate.
  - Verified against the showcase books: on an empty future period all eight are clear; on the current month three are blocking - the deliberate drafts, the unmatched statement, and a box with tax and no base.
- [x] Filing freezes a **snapshot** - the figures, the supporting line ids and a hash - which cannot change afterwards even if the underlying data is later adjusted. A trigger refuses every UPDATE and DELETE, not just one to the figures: once one column can move, the argument for the next is already made. A check posts more tax into the period after filing and asserts the filed figures did not move
- [x] Filing is permissioned, requires MFA, and is audited. Through `Support`'s `RequiresStepUp` and `AuditTrail` interfaces, because the layer rules do not let Tax depend on Identity - and the audit record carries the checklist as it stood, which is the evidence it was looked at
- [x] A filed return is re-printable byte-identically, which is what gets attached to a query from the authority. The canonical bytes are **stored**, not recomputed: recomputing relies on the canonicaliser never changing, which is a promise about future code made about a document an authority may query in six years
- [x] A journal line gained a `tax_point`, **paired with its tax code by a CHECK**. That pairing makes the return complete by construction - every tax-bearing line falls in exactly one return period - rather than complete as far as anybody has checked. The reverser carries the original over, so a reversal of a May supply belongs to May's return rather than to whenever somebody noticed
- [x] Each box carries its **taxable amount as well as its tax**, because the authority's arithmetic is amount times rate and a figure with no base is one nobody can verify. Which side a line is on comes from the **account** it posted to, not from its code: a standard-rate code appears on a sale and a purchase, and the bite that derived the side from the code reported 110.00 of output tax instead of 150.00
- [x] The **net due is computed**, output less input, rather than read from a box a code could post into - which would be a return whose bottom line disagreed with its own boxes
- [x] The checklist reports the three checks it **cannot run yet as pending, with the phase that brings them**. A checklist that silently omits a check tells the person filing that everything was looked at, which is the one thing it must never do
- [x] The override exists and demands a sentence. Refusing outright would be wrong - a controller sometimes files with a known problem because the deadline is today and a penalty is worse than a disclosed error - but filing over a checklist silently must not happen, so the reason goes in the audit record and "override" is refused as one
- [x] Found on the way: the step-up prompt read "Set up a second factor before you 2026-05". The label is documented as a **noun** and the message template expected a verb phrase, so the prompt read as a mistake - which is a prompt people click past. It now reads "before continuing with 2026-05"
- [x] Found on the way: every filing rule failed under `bin/verify all` and passed under `bin/verify tax`. An earlier suite leaves a signed-in user on the guard, and `tax_return.file` demands a factor that user has not enrolled - the guard working correctly, on somebody else's session. The suite now sets the auth state rather than inheriting whatever ran first

> The open criterion is the checklist's own contents: three of its four named items - unposted documents, unmatched bank lines and missing evidence - inspect things that arrive in Phases 05 and 08. They are **listed as pending with their phase** rather than omitted, and five checks that can run do run and do block.
