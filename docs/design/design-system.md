# Design system

**The brief for a financial application is legibility and velocity, not delight.** People live in these tables for eight hours, type numbers faster than they can point at them, and need to trust what they read at a glance. Every decision below follows from that.

Distinctiveness comes from restraint executed precisely — tabular figures that actually align, a density the user chose, a focus ring that is always visible, an accounting negative that reads correctly to someone who cannot see red. Not from gradients.

## Token architecture

Three layers. **A component never references a primitive.**

```
primitive   --p-navy-500: 62.5% 0.12 263            ← raw ramps, no meaning
     ↓
semantic    --c-primary: var(--p-brand-navy)          ← a role
     ↓
component   --k-scrollbar-thumb: var(--color-outline-strong)   ← what a component owns
```

**The component layer is `--k-`, not `--c-`** — PF-199. Every `--c-*` is read as a
semantic role by `php bin/verify design`, which requires each one to be redefined
by all five themes and to appear in `contrast-pairs.json`; a component token has
neither property, because it is derived from a role and measured through it. The
third layer therefore needs a name of its own, and having one is what turns "a
component never references a primitive" into something a check can decide rather
than a convention a reviewer has to remember. The layers, what each may read, the
role each token family stands for and every token that deliberately does not
invert are declared in [`resources/css/token-architecture.json`](../../resources/css/token-architecture.json).

In CSS, the two-layer mapping that makes the theme work with no `dark:` at the call site:

```css
:root { --c-primary: 54.1% 0.192 258.3; }
.dark { --c-primary: 78.4% 0.118 254.1; }

@theme { --color-primary: oklch(var(--c-primary)); }
```

`text-primary` now follows the theme everywhere.

### Why OKLCH

Perceptual uniformity. A ramp generated by stepping lightness **looks** evenly stepped, and a contrast target is hit by adjusting one number rather than by trial and error. In hex or HSL, `#3b82f6` and `#8b5cf6` at the same nominal lightness look nothing alike, and every palette adjustment is a renegotiation with the contrast checker.

A token may only be added **with a stated role**. A token named after a colour rather than a role fails review, because `--c-blue` cannot be re-themed and `--c-primary` can.

### Tokens that deliberately do not invert

Some surfaces are always dark and always carry light text — the sidebar, a primary container. These are documented as fixed with the reason, so nobody "fixes" them later.

"Does not invert" is **measured**, not asserted: the light theme's resolved colour against Graphite's, for every role, on every run. Seven roles are fixed — the six sidebar roles and `outline-control`, which is a single mid tone in both themes because it is the one line whose contrast is *required* (3:1, 1.4.11) and a mid tone is what clears 3:1 against a near-white surface and a near-black one at once. `outline-control` had been fixed in both themes and said nothing about it until PF-199 measured it, which is exactly the shape of the thing this section exists to prevent.

### The focus indicator is two colours

A ring and a halo, `--c-focus-ring` and `--c-focus-halo`, with the halo filling the 2px `outline-offset` gap. Not a flourish: a single-colour ring **cannot** satisfy 1.4.11 here. Measured, Graphite's ring and a primary button are both Glacier Teal — a 1.00:1 indicator on the main action — and in the high-contrast themes the constraints "4.5:1 from a near-white surface" and "4.5:1 from a Glacier Teal fill" have an empty intersection, so no single colour exists. The rule the matrix holds is that for every fill a focused control can have, at least one of the two clears the target, and the two clear it against each other.

The halo is drawn with `box-shadow` from an **unlayered** rule, so it beats a `shadow-*` utility on the one focusable element that carries its own elevation (the sign-in CTA). A focused control trades its drop shadow for two rings while it is focused, which is the right trade.

## Colour

> ### ⚠️ The dark variant must be redefined, and this one line is load-bearing
>
> ```css
> @custom-variant dark (&:where(.dark, .dark *));
> ```
>
> Tailwind v4 defaults `dark:` to `@media (prefers-color-scheme: dark)`. PeakFlow toggles a `.dark` class, so **without that line every `dark:` utility silently does nothing** — the utility compiles, the class lands in the HTML, and the colour never changes.
>
> This is inherited as a known trap from a sibling project where it shipped: a status pill measured **1.62:1** against its background in dark mode, and **11.75:1** after the fix. Nothing failed; it just looked slightly off to people who could see it and was invisible to people who could not.

### Semantic colour for finance, never colour alone

**WCAG 1.4.1** is not negotiable here, and finance has a specific trap: variance columns.

| Meaning | Treatment |
|---------|-----------|
| Debit / positive | **Neutral foreground.** Money is not good news by default, and colouring every positive green makes the page shout |
| Credit / negative | Accounting negative: **parentheses, a sign, and a colour** — `(1,234.56)`. A colour-blind user reading a variance column needs the parentheses |
| Overdue | Colour, an icon, **and the word** |
| Reconciled / matched | A check glyph plus a text state, never a green row alone |
| Draft / unposted | A hatched leading border and the literal word "draft", **including on print** |
| Disputed | A distinct state, not a shade of overdue — they require different actions |

### Contrast is verified, not reviewed

A test computes the ratio for **every legitimate foreground-background pair in both themes** and asserts 4.5:1 for text and 3:1 for UI components and graphical objects. The legitimate pairs are declared, so the test knows what is intended rather than testing a cartesian product. A palette change that regresses any pair fails the build. Focus indicators are tested separately against both the component and the adjacent background, per **2.4.11**.

## Typography

| Role | Face | Notes |
|------|------|-------|
| UI, Arabic and Latin | A variable Arabic-capable sans | Self-hosted, vendored through the asset pipeline |
| **Numerals** | A variable Latin face with **tabular figures** | Used for every figure, including in Arabic UI |
| Monospace | For references, hashes, IBANs | Where character-level verification matters |

**Nothing is fetched from a third party at runtime.** Fonts are served from the hashed build output, so an offline load keeps its typography and no third party learns who is using the application.

### Tabular numerals, everywhere

```css
.figure { font-variant-numeric: tabular-nums; font-feature-settings: "tnum" 1; }
```

Applied to every figure in every table, every total, every chart axis and every tooltip. **A proportional `1` in a currency column is the single most common reason a financial UI feels amateur** — the thousands places do not line up, and the eye cannot scan the column.

The Arabic and Latin faces are chosen with **matched x-height and vertical metrics**, so a mixed line does not jump. Line height accounts for Arabic's taller ascenders and deeper descenders; a scale tuned on Latin text crowds Arabic.

### Digit shaping

Per-tenant (`latn` / `arab`), applied through **ICU, never by string replacement**. Western digits are the default because financial documents in the region conventionally use them; the setting exists because institutional convention differs.

Shaping is **display only**. Stored values, exports, XML payloads and API responses are always Western digits, and a test asserts an Arabic-shaped display value still parses and round-trips.

## Density

Three modes, changing row height, font step and padding **through tokens alone**:

| Mode | Row height | For |
|------|-----------|-----|
| `comfortable` | 48px | Occasional use, touch, smaller screens |
| `compact` | 40px | The default |
| `dense` | 32px | An accountant on a large monitor who wants 40 rows visible |

**A user setting, not a breakpoint.** A default that serves one user serves neither. Persisted per user and applied **before first paint**, so the layout does not reflow on load.

Target sizes stay within the **24×24 minimum (WCAG 2.5.8) in every mode, including `dense`** — which is the constraint that bounds how dense `dense` can be.

## Spacing, radius, elevation

| Scale | Values | Note |
|-------|--------|------|
| Spacing | 4px base, `4 8 12 16 20 24 32 40 48 64` | Density scales the applied step, not the scale |
| Radius | `0 4 6 8 12 16 full` | One radius per component role; a card and a button do not share |
| Elevation | Five levels, each a token pair (shadow + border) | Dark mode uses border emphasis over shadow, because shadow is nearly invisible on a dark surface |

## Components

| Component | The requirement that shapes it |
|-----------|-------------------------------|
| **Data grid** | 50,000 rows, keyboard editing, frozen columns, saved views. The product's centre of gravity — see [`interaction-and-motion.md`](interaction-and-motion.md) |
| **Figure cell** | Tabular, right-aligned in LTR and **still right-aligned in RTL** (numbers do not flip), accounting negative, currency-aware exponent |
| **Currency input** | Masks as you type, accepts Arabic and Western digits, accepts a pasted value with separators, respects the currency's exponent, **never silently truncates a third decimal** |
| **Date-range picker** | Understands **fiscal periods**: "last period", "this quarter", "year to date" resolve against the entity's own calendar, not the Gregorian one |
| **Account picker** | Tree-aware, code-first search, shows the control role, **refuses a control account with an explanation rather than hiding it** |
| **Dimension picker** | Validity rules applied live; an invalid combination is explained |
| **Status pill** | Colour **and** icon **and** word. The 1.62:1 lesson lives here |
| **Drill-down panel** | One mechanism for the whole application, not per report |
| **Reconciliation split view** | Running difference always visible; keyboard parity for every drag |
| **Invoice builder** | **Server-authoritative totals**, with a visible pending state and no optimistic rendering |
| **Approval trail** | Who, when, what state they approved, and what invalidated a prior approval |
| **Period indicator** | The active entity and period state on every screen — a user posting into the wrong company or a closed period is what it prevents |
| **Table footer** | Page-size selector (allowlisted 10/50/100) that re-emits active filters, plus a themed paginator built from the paginator's own methods so it matches the design system in both themes and under RTL |
| **Scrollbar** | Furniture, in the design system's own colours rather than the operating system's. One `--k-scrollbar-*` component token read by BOTH syntaxes — `scrollbar-color`/`scrollbar-width` for Firefox, `::-webkit-scrollbar` for Chrome and Safari — so the two cannot drift into two products. The sidebar swaps one declaration, not a second set of rules. Measured against every surface it sits on in all five themes (3:1, 4.5:1 in high contrast): **a scrollbar styled into invisibility is a worse product, not a cleaner one**. `scrollbar-gutter: stable` on every scroller, which puts the gutter on the left in Arabic without naming a side |

## Print

**A first-class medium**, not an afterthought — the print view is what gets attached to an email and archived.

- A4 **and** Letter; correct margins in both
- Page breaks that never split a table row or orphan a total; repeated table headers; `page x of y`
- Entity identity, report parameters and the as-of basis **on every page** — a printed report without its parameters is unusable
- No interactive chrome, no colour-only meaning, and a draft watermark that is **also a word**
- **Tested by rendering and diffing the PDF**, not by eyeballing a browser preview

## Known traps, recorded where they bite

| Trap | Consequence | Guard |
|------|-------------|-------|
| Missing `@custom-variant dark` | Every `dark:` utility silently does nothing | Present with a comment; contrast test would catch the result |
| `npm run build` straight after `php artisan view:clear` | The build scans compiled Blade via `@source`; with that directory emptied it succeeds, says nothing, and ships a stylesheet **missing ~18 kB of utilities** that only appear in compiled templates | `view:cache` first, or build before clearing. Documented in `CONTRIBUTING.md` |
| A `tailwind.config.js` | **Not read.** Tailwind v4 is configured in CSS | No such file, with a comment saying adding one will not work |
| Native `<select>` arrow | Renders on the wrong side under RTL and ignores the theme | An unlayered rule with inline SVG chevrons positioned on the inline-end side, kept outside Tailwind's layers so its padding wins |
| Icon fonts | Ligature-based, so the literal word shows before the font loads | Icons hidden until the font is ready, flag read synchronously from `sessionStorage` before first paint, with a `<noscript>` reveal |
| A proportional numeral in a table | The column cannot be scanned | `.figure` with `tabular-nums` on every numeric cell |
| Shadow-only elevation | Nearly invisible on a dark surface | Elevation tokens pair shadow with border, weighted per theme |
